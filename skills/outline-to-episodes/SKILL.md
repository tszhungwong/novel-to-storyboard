# 大綱轉分集

拆鏡（`novel-to-storyboard` 技能）從一場戲開始。這個技能處理更前面的事：手上只有大綱，或要做成固定長度的短集時，怎麼決定每一集演什麼、寫出每一集的劇本，再交給拆鏡。

回覆語言跟隨使用者，預設繁體中文。

**檔案在哪裡。** 這個技能和 `novel-to-storyboard` 裝在同一個 plugin 裡，共用它的腳本與欄位定義。下面寫的 `../novel-to-storyboard/` 是相對於這個技能資料夾的路徑：

- 腳本：`../novel-to-storyboard/scripts/build_storyboard.mjs`
- `series.json` 與 `bible.json` 的欄位：`../novel-to-storyboard/references/fields.md`
- 拆鏡流程：`../novel-to-storyboard/SKILL.md`

完整範例在這個技能的 `examples/`：一份十二集的大綱、第一幕的分集表，和第一集的分集劇本。

## 一、什麼時候用

- **輸入是大綱**：故事大綱、梗概、分集大綱、人物小傳加劇情走向。它們只說「發生了什麼」，沒有對白，也沒有逐場的動作。直接拆鏡的話，台詞只能邊拆邊編，結果是一句大綱對一鏡，每集長短也失控。
- **使用者給了單集長度**（「每集 60 到 90 秒」「一集一分鐘」），而原文要拆成很多集。小說也一樣要先做分集表；但小說已經有對白和動作，跳過第四節的分集劇本，直接拿原文拆鏡。
- 已經有場次、有台詞的分集劇本，是拆鏡流程第一步說的「劇本」，直接用 `novel-to-storyboard`。
- **只要劇本、不拆分鏡**（要自己拍、交給別人拆，或先看劇本再說）：做到分集劇本為止，每一集交付劇本和第四節的長度檢查；之後要拆鏡，再交給 `novel-to-storyboard`。

## 二、四層資料，三次確認

| 層 | 內容 | 檔案 |
|---|---|---|
| 大綱 | 使用者給的原文 | 不動 |
| 分集表 | 每一集演到哪裡、鉤子、爽點、卡點、出場角色與場景 | `storyboard/series.json`，腳本產出 `series.md` |
| 分集劇本 | 一集的場次、畫面、台詞與旁白 | `storyboard/EP01-script.md`，一集一個 |
| 分鏡 | 見 `novel-to-storyboard` | `storyboard/EP01.json` |

越上層的錯越貴：分集切錯了，劇本和分鏡都要重做；台詞的語氣不對，每一集都要改。而每往下一層，加進去的東西就有越多是原文沒有的。所以：

0. **動手前先問參數**：讀 `../novel-to-storyboard/SKILL.md` 第二步，照它的做法和題目一次問完。大綱要多問兩題：大綱沒寫的話，單集長度與集數；付費或留存卡點放在哪幾集。大綱已經寫了的不問。形式、媒材、工具、聲音這幾題也在這一次問，拆鏡時就不用再問一輪。
1. **分集表做完一定停**，等使用者確認，再寫劇本。
2. **第一集的劇本寫完停一次**，請使用者確認台詞風格、旁白人稱和長度。這幾件事定了，後面的集數照著寫。
3. 之後每一集的**劇本和分鏡一起做、一起交付**：劇本寫好、檢查過長度，就照 `novel-to-storyboard` 拆那一集。使用者改了劇本，就重拆那一集。

拆鏡流程第四步「不只一個地點或超過 30 鏡就先停」的規則，在這個流程裡由上面三個確認點取代。使用者事先說「直接做完」就不停（參數照樣先問，除非也說了「不用問」），但交付時仍然要把分集表和第一集的台詞風格列出來給他看。

## 三、分集表

### 先讀出大綱已經決定的事

很多大綱已經寫了集數、單集長度、分幾幕、每幕幾集、轉折點落在哪裡、一個單元故事最多幾集、開篇要做到什麼。有寫的照用，不要重新規劃；沒寫的照下面的方法定，列入待確認。

**付費卡點、留存卡點**放在哪一集，是平台與商業上的決定。大綱有寫就標出來（`paywall`）；沒寫就在動手前的問題裡問，使用者也不知道就先不標，不要自己挑。

### 一集裝得下多少

以 60 到 90 秒的豎屏短劇或漫劇來說，經驗上大約是（單集更長的動畫或真人劇，照比例放大，地點與場次可以多一些）：

- **一個核心事件**：一個爽點，或一個轉折，加上開頭的鉤子和結尾的卡點。
- **兩到四場戲，地點不超過三個。** 每多一個地點，就多一張場景定稿圖、多一次建立鏡頭。
- **二十到三十五鏡。**
- **台詞加旁白大約 200 到 300 字**：目標秒數 × 語速（每秒 4.5 字）× 0.75。乘 0.75 是因為鉤子畫面、反應鏡頭和停頓的時候沒有人說話。旁白一路講到底的解說型漫劇可以放寬到 0.9。

大綱的密度不平均。「他把她送進幼兒園，她一哭全班跟著哭，園長當場辭退」一句話就撐得起一整集；一大段世界觀說明可能一個鏡頭都不需要，拆散到用得上的那一集再交代。所以**按事件切，不按段落或字數切**。

### 怎麼切

1. **列事件**：把大綱裡發生的事一件一行列出來：誰做了什麼，結果是什麼。
2. **標份量**：每件事是轉折、爽點、主線線索，還是過場。
3. **一集一個中心**：每集以一個爽點或轉折為中心，前面帶上它需要的鋪陳。過場的事併進相鄰的集，或用一句旁白帶過。
4. **切在懸念上**：一件事做到一半、新資訊剛露出來、決定還沒做出來。不要切在事情完整結束、大家都鬆一口氣的地方，觀眾就是在那裡滑走的。
5. **對集數**：每一幕的集數要對上大綱。多了就把過場併掉；少了不要灌水，回頭找大綱裡被一句帶過、其實撐得起一集的事（兩人第一次正面交鋒、一次失敗的嘗試）。為了撐起一集而新增或調動的情節，記在那一集的 `added`。
6. **省資產**：同樣的戲，能在已經有的場景裡發生，就不要為它開一個只用一兩鏡的新場景。真的要新增的角色、場景、道具，記在那一集的 `new_assets`，使用者才能提前準備資產圖。推動劇情的道具也算：出現在鉤子、爽點或卡點裡的東西（投訴單、辭呈、一只啤酒杯），就算只出現一集，也要在 `bible.json` 的 `props` 或那一集的 `new_assets` 裡。

### 每一集回答四個問題

| 欄位 | 問題 | 寫法 |
|---|---|---|
| `hook` 鉤子 | 前三秒觀眾看到什麼？ | 寫成一個畫面，不是一句旁白 |
| `payoff` 爽點／核心事件 | 這一集觀眾等到了什麼？ | 一句話：誰對誰做了什麼，結果如何 |
| `cliff` 卡點 | 結尾留下什麼問題？ | 最後一個畫面，加上觀眾心裡會問的那個問題，用問號結尾：「周先生說押她記憶的是外婆。外婆為什麼要押她的記憶？」只寫事件，寫劇本和拆鏡時就不知道要停在誰的反應上；沒有問號腳本會提示 |
| `thread` 主線推進 | 主線往前走了什麼？ | 線索、倒數、關係的變化。單元集也要有一點，否則觀眾覺得在原地踏步 |

**鉤子的四種做法**

| 做法 | 例 | 注意 |
|---|---|---|
| 接住上一集的卡點 | 開頭重播上一集的最後一鏡，接著給答案，或讓情況更糟 | 上一集生成好的鏡頭可以直接重用，不必再生成；分鏡的 `continuity` 註明重用哪一鏡 |
| 本集高點提前 | 先給本集最緊張的一個畫面，再接「三分鐘前」 | 這是調動順序，記在 `added`；跳回去時用轉場或旁白標出時間 |
| 反常的畫面 | 一個不合常理的特寫：會眨眼的照片、開口說話的貓 | 本集內要給出解釋，或至少往前推一步 |
| 從衝突中途切入 | 直接從追逐或爭吵的一半開始 | 前因用一兩句台詞補 |

**卡點的五種類型**（填在 `cliff_type`）

| 類型 | 意思 |
|---|---|
| 危機 | 角色馬上要出事：被抓、被識破、倒數到了 |
| 揭露 | 一個新資訊推翻了原本的認知 |
| 反轉 | 以為贏了其實輸了，或反過來 |
| 抉擇 | 角色必須在兩個代價之間選一個 |
| 登場 | 新的人物或威脅出現在門口 |

連續三集用同一種，觀眾會疲乏，腳本會提示。類型照卡點的內容填；為了避開提示而改標籤沒有用，要改的是卡點本身。

### 爽點怎麼排

爽劇的一個爽點通常有四段：

1. **壓**：主角被看不起、被逼到角落。要短，觀眾等的是後面。
2. **揚**：主角出手：用能力、談判、揭穿。
3. **看**：旁人的反應。反派的表情垮掉、圍觀的人愣住、對手手上的東西掉下來。這一段最容易被省略，但爽感有很大一部分是從這裡來的。寫劇本時給它畫面，拆鏡時給它反應鏡頭和停頓。
4. **收**：結果落地，接到卡點。

不是爽劇也一樣：每集的核心事件之前要有阻力，之後要有人對它起反應，觀眾才感覺得到它的份量。

### 開篇幾集

- 前三集要交代清楚：主角是誰、他要什麼、他被什麼困住、他的金手指或這個世界的核心規則。
- 第一集的第一個畫面，用整季最抓人的意象。
- **規則用演的，在用得上的那一刻才交代**，一集最多一條新規則。一開場就用旁白講完世界觀，觀眾會滑走。

### 跨集要記住的事

- **會累積的狀態**：倒數計時、分數、傷勢、關係的進展。每一集結束時的值寫在 `state`，劇本和分鏡照它畫，下一集也從這裡接。
- **單元故事的長度**照大綱的上限；大綱沒寫，一個單元以兩三集為原則。
- **口頭禪**：大綱給了就用，但留給關鍵時刻。每集都說，很快就變成噪音。

### 一次排多少集

先給全季的結構（每一幕從第幾集到第幾集、每一幕結束在哪個轉折），讓使用者看到整體的形狀；詳細的分集表一次排一幕，或十到十五集。一次排完幾十集，後面的集數多半要在寫劇本時重排。

設定檔也照這一批來建：這一批會出場的主要角色和反覆出現的場景先寫進 `bible.json`，有台詞的主要角色連聲線（`voice`）一起定，整季才是同一個聲音；只在後面某一集出現一次的，先記在那一集的 `new_assets`，拆到那一集時再補。

### 交付分集表

執行腳本，產出 `series.md` 與這一批的設定表：

```bash
node <這個技能的資料夾>/../novel-to-storyboard/scripts/build_storyboard.mjs storyboard/bible.json storyboard/series.json
```

交付前自己對一遍，這幾件事腳本看不出來：

- **分集表和設定檔不矛盾。** 分集表裡寫到的造型、傷勢、道具狀態，和 `bible.json` 的造型變體一致（設定寫辮尾綁著紅橡皮筋，分集表就不能寫「散開的辮子」）；寫到的時間、天氣，和那一集用的場景一致（用了大雨的場景，就不能寫「走進雨停的街上」）。改了其中一邊，另一邊一起改。
- **一集最多一條新規則，每一集都是。** 大綱一開場就有好幾條規則（城隍爺不見了、誰撿到誰處理、滿七張許願）時，第一集只演最急的那一條，其餘排到用得上的那一集；第二集也不要把剩下的兩條一起補上。
- **劇情道具都有登記。** 鉤子、爽點、卡點裡寫到的道具，都在 `bible.json` 的 `props` 或那一集的 `new_assets` 裡；後面每一集都會看到的佈景物（攤位上的電風扇）寫進場景的 `space` 或登記成道具。
- **自己補的都列進 `pending`。** 大綱沒寫的外貌、聲線、口頭禪、時代與地點細節，每一項都在 `pending` 裡，交付分集表時請使用者確認；主角的聲線常常被漏掉，它還可能是整季旁白的聲音。
- **上一集的結尾接得上下一集的鉤子。** 上一集 `state` 寫的造型、傷勢、道具狀態，就是下一集鉤子的起點；鉤子接住上一集的最後一刻，人物就還穿著那一刻的衣服。
- **聲音方案配得上對白量。** 漫劇預設「旁白」，角色全程不開口；大綱裡角色之間來回說話的戲很多時，動手前的聲音題目要同時列出「後配口型」與「原生音訊」的代價，讓使用者決定。短劇、動畫與真人劇本來就以對白為主，旁白只用在交代時間跳躍或主角的心聲。

在對話裡依序給：

1. 本次參數（動手前確認過的），以及使用者沒回答、先用建議值的地方。
2. 全季結構：每一幕的集數範圍與結尾的轉折。
3. 這一批的分集表：集數、一句話劇情、鉤子、卡點、預估秒數。完整的表在 `series.md`。
4. 新增或調動的情節，以及大綱沒說清楚、先自己決定的地方。
5. 這一批用到的角色與場景設定，分清楚哪些來自大綱、哪些是暫定。
6. 請使用者確認，說明確認後先寫第一集的劇本。

## 四、分集劇本

一集一個檔案：`storyboard/EP01-script.md`。格式固定，腳本才讀得出台詞、算得出長度：

```markdown
# EP01　開張

- 鉤子：木格櫃裡的玻璃珠，每一顆裡面都有一個小小的人影在動
- 爽點：午夜一到，黑貓開口說話，當鋪真正的生意出現在小禾面前
- 卡點：第一位客人推門進來，問這裡能不能當記憶。小禾收，還是不收？

## 第 1 場　當鋪店內・下午　日　內

人物：沈小禾、墨墨
目的：用一個反常的畫面抓住觀眾；交代小禾接手了外婆的當鋪，只想賣掉

△ 大特寫：木格櫃裡的一顆玻璃珠，珠子裡有一個小小的人影在走動。
旁白：外婆留給我一間當鋪，一屋子玻璃珠，還有一筆債。
沈小禾（小聲）：……一定是我太累了。
【字】手機訊息：「沈小姐，鋪子明天就能簽約。」
```

- **場標**：場號、地點、時段、內外。地點用設定檔裡的場景名稱。
- **人物、目的**：目的就是拆鏡時 `plan` 的 `purpose`。
- **△ 開頭的是畫面**：只寫拍得到的東西，原則和拆鏡流程第一步改寫小說一樣。一行是一個節拍，不是一鏡；拆鏡時一行可能變成兩三鏡。
- **台詞**：`角色名（語氣）：台詞`，語氣可以省略，角色名用設定檔裡的名稱。不是當場說出口的，寫在括號裡：`沈小禾（內心獨白）：…`、`阿傑（畫外音）：…`。敘事者寫 `旁白：…`。
- **【字】開頭的是後製文字**：花字、手機訊息、介面上的數字、信件內容。字幕不用寫，它就是台詞。

### 台詞怎麼寫

- **短。** 一句盡量在 20 個字以內，大約 4.5 秒，一鏡講得完。長的話拆成幾句，中間插反應。
- **畫面已經演了的，台詞不要再說一次。** 她把信推過去，就不用說「我把信給你」。
- **旁白只做三件事**：交代時間或地點的跳躍、說出畫面拍不出來的資訊（規則、過去發生的事）、主角的心聲或吐槽。不要描述觀眾正在看的東西。
- **旁白的人稱全季一致**，寫在 `bible.json` 的 `project.narration`（例如「沈小禾的第一人稱自述」）。
- **每個角色說話要分得出來。** 從大綱給的性格決定句子長短和用詞：嘴貧的人話多、愛反問；冷靜的人句子短、不用語氣詞。蓋住名字讀台詞，應該猜得出是誰說的。
- **△ 寫成看得懂的畫面。** 打鬥寫出每一下的結果與旁人的反應，觀眾才知道誰佔上風；長段要讀的文字（訊息、信件、字卡）寫成【字】。劇本照戲寫，不用先替生成工具避開什麼：工具定了、某些拍法它做不好，拆鏡時再換拍法，劇本不用改。

大綱沒有台詞，台詞都是新寫的，交付時說一次就好，不必逐句標示。情節上的新增或改動仍然記在分集表的 `added`，拆鏡時寫進 `changes`。

### 檢查長度

寫完執行：

```bash
node <這個技能的資料夾>/../novel-to-storyboard/scripts/build_storyboard.mjs storyboard/bible.json storyboard/EP01-script.md
```

腳本會算出台詞與旁白大約要講多久、和 `project.episode_length` 比較，列出一鏡講不完的長句，以及不是設定檔角色名的說話者。台詞超過單集上限的四分之三，拆鏡後幾乎一定超長：先刪句子，不要等到拆鏡才發現。

## 五、從劇本到分鏡

照 `novel-to-storyboard` 拆鏡（讀 `../novel-to-storyboard/SKILL.md`），把分集劇本當成它第一步的「劇本」，照第五步拆。參數在這個技能的第 0 步已經問過，不用再問。和一般劇本不同的地方：

- 劇本的每一場寫成一筆 `plan`：場的目的是 `purpose`，△ 與台詞的轉折是 `beats`，爽點所在的節拍是 `peak`。
- **台詞照劇本，一字不改。** 要改就先改劇本，劇本是台詞唯一的來源，否則兩份文件會越來越不一樣。
- `source` 填劇本的位置，例如「第 2 場第 3 行」，或照抄那一行的開頭。
- 前三秒內要看到鉤子。卡點的最後一鏡停在問題上，不給答案，可以比一般的鏡頭長一點，讓觀眾停在那裡。
- 腳本會在分鏡表最上面列出這一集在分集表裡的鉤子、爽點與卡點，並用 `episode_length` 檢查整集長度：
  - **太長**：先刪台詞、合併過場鏡頭。還是太長，把一個節拍移到下一集，同時改分集表。
  - **太短**：不要用放慢的鏡頭撐。補「看」那一段的反應鏡頭、插入鏡頭，或把下一集開頭的內容提前。
- 單集在兩分鐘以內時不用標 `cut`，一集本身就是成品的長度。

做完一集，除了在 `bible.json` 的 `log` 加一行，也確認分集表裡這一集的 `state` 和實際拍出來的一致；有出入就改分集表，下一集從這裡接。

## 六、接著做下一集

在新的對話裡接著做時，先讀 `bible.json`（包含 `log`）與 `series.json`，從還沒做的下一集開始。分集表只排到這一批的最後一集時，先排下一批、停下來確認，再寫劇本。
